# Code Atlas

Code Atlas indexes a group of Rust and TypeScript repositories into one SQLite knowledge graph per project and serves it to coding agents over a CLI (`catl`) and an MCP stdio server.
Every fact carries provenance (certainty + evidence), and no query answers from an index older than the working tree.

## Crates (`crates/`)

- `atlas-core` — ids, keys, kinds, certainty/evidence, the `FileFacts` IR, analyzer/detector/LLM traits, errors
- `atlas-store` — SQLite schema, migrations, per-file fact ownership, traversal primitives, run ledger
- `atlas-project` — project registry, cwd inference, worktree detection and overlay state (`worktrees.json`), discovery, hashing, stat cache, manifests, layered configuration and route-family definitions (`<config dir>/detectors/*.toml`, hence its dependency on `atlas-detect`)
- `atlas-lang-rust` / `atlas-lang-ts` — tree-sitter analyzers producing `FileFacts` (depend on core only)
- `atlas-resolve` — Rust module/use and TS import resolution, call targets with certainty
- `atlas-detect` — framework detectors: endpoints, clients, auth, env/config, tests, events, jobs, db
- `atlas-scip` — SCIP generation/ingestion that upgrades edges to `compiler_verified`
- `atlas-similarity` — MinHash/LSH near-duplicates and BM25 search
- `atlas-semantic` — `LlmProvider` backends, call cache and ledger, inferred facts
- `atlas-link` — cross-repo links: packages, API↔client, auth, events, config
- `atlas-engine` — full/incremental pipeline, lineage, freshness barrier, watcher
- `atlas-query` — query surface shared by CLI and MCP
- `atlas-lsp` — blocking stdio JSON-RPC client, LSP types, server processes and pool, document sync (core only, no project or engine)
- `atlas-edit` — edit plans, path-guarded atomic application with rollback, text operations, symbol regions (no LSP, no engine)
- `atlas-ide` — `IdeService`: exact operations over language servers plus graph extras, shared by CLI and MCP
- `atlas-test-lsp` — unpublished test crate owning the only fake language-server binary (`atlas_test_lsp::fake_lsp_path()`) and the hermetic `catl` spawn helper (`atlas_test_lsp::hermetic`); no product build includes it
- `atlas-mcp`, `atlas-cli` (binary `catl`), `atlas-bench`, `atlas-eval`

The plans live in `docs/plan/implementation-plan.md` and `docs/plan/ide-operations-plan.md`. `atlas-lsp`, `atlas-edit` and `atlas-ide` have their own `CLAUDE.md` with the language-server, edit and IDE-service contracts; do not duplicate them here.

## Rules

- Never present heuristic or inferred knowledge as certain. Every edge and derived entity carries exactly one `Certainty`. Query output may state a fact as known only if `Certainty::is_authoritative()` is true; every other fact carries its tag (`[heuristic 0.72]`, `[inferred 0.81 stale]`).
- `Certainty::is_llm_derived()` (only `Inferred`) separates LLM facts, which can go stale, from file-owned reproducible facts. Uncertainty is never silently upgraded.
- `atlas-core` contracts are append-only: add items or `#[non_exhaustive]` variants, never change existing signatures or key formats. `EntityId` values are pinned by tests; changing key rendering is a breaking change.
- Language-server answers render as `[compiler]` but are never stored and never become graph facts; the rest of the contract is in `crates/atlas-ide/CLAUDE.md`.
- Source edits (`atlas_edit`, CLI `edit`) are applied only by `atlas-edit` inside `Engine::write_then_refresh`; language servers never write (`crates/atlas-lsp/CLAUDE.md`). The MCP server is therefore not read-only: `atlas_edit` is its only mutating tool (15 tools; `atlas_read` and `atlas_changes` were folded into `atlas_symbol mode=source` and `atlas_status since_run`). `[mcp] tools` (`catl mcp --tools`) serves a profile of them: `full` (default, all 15), `core` (`atlas_context`, `atlas_search`, `atlas_symbol`, `atlas_impact`, `atlas_edit`, `atlas_status`), `read-only` (`core` without `atlas_edit`) or a list; `atlas_mcp::guidance::ToolProfile` is the only place that resolves it, a tool outside the profile is unlisted and its calls are refused, and no tool description may name another tool, so every description holds in every profile. An MCP server started where no project resolves (no `--project`, no marker, no registered repo containing its cwd), or in a git worktree while `[worktrees] mode = "off"`, runs in unbound mode and serves only `atlas_status`.
- CLI exit codes: 0 results, 1 error, 2 usage, 3 degraded, 4 nothing matched (read commands only), 5 edit refused (nothing written; never 4), 6 edit rolled back, 7 edit partially applied (never 0), 130 interrupted. After a signal deferred during a write, the exit is 5, 6 or 7 if the edit was refused, rolled back or partially applied, and otherwise 130, never 0 (`interrupt::exit_after_signal`). A change to an edit outcome must keep these mappings (`atlas-cli/src/error.rs`).
- Agent guidance has one source, `atlas_mcp::guidance` (`crates/atlas-mcp/src/guidance.rs`): the MCP `instructions` and the repo block `agents sync` writes are renderings of it for the configured tool profile (a rule or clause appears only when the profile has every tool it names), and a test checks that `docs/agent-integration.md` shows exactly the rendered `full` block. Change the rules there, never in a copy. Every profile with `atlas_edit` must keep saying: `atlas_edit` for renames and symbol rewrites, re-read a file after `atlas_edit` changed it; every profile with `atlas_symbol` must say `atlas_symbol mode=source` only for code the agent will not edit itself. Each clause names only the tools in its `needs` (tested). An invalid `mcp.tools` from any layer fails `catl mcp` and `doctor`, never widens the tool set, and `agents sync` resolves the profile from `config.toml` alone. Its `READ_ONLY_TOOLS` must equal the tools annotated read-only (`atlas-mcp/tests/protocol.rs`), and `agents sync` writes as `permissions.allow` rules exactly those of them in the profile (`ToolProfile::read_only_tools`); `atlas_edit` is never in it. The eval preambles are versioned experimental conditions, not renderings.
- Agent wiring (`catl agents sync|status|unsync`; `connect claude` keeps its earlier per-repo behaviour and is recorded too) records what it wrote in `<data dir>/wiring.json` with a hash of the fragment it owns, never overwrites or removes a fragment changed since without `--force`, and registers Claude Code user and local entries only through the `claude` CLI. `agents sync` never pins `--project` and names an absolute command only when `[agents] binary` is one (never in project scope); unrecorded entries with either (such as those `connect claude` writes) are what `--migrate` replaces. After `claude mcp add-json` it reads the entry back and fails if it is absent; a failed add restores the previous entry. Tests start `catl` only through `atlas_test_lsp::hermetic::hermetic_catl` (sandboxed `HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `CODE_ATLAS_HOME`, `PATH` = fake bin + `/usr/bin:/bin`), which `scripts/check.sh` enforces by grep, and `sync`, `unsync` and `connect` refuse when `CARGO_MANIFEST_DIR` is set without `CLAUDE_CONFIG_DIR` and `CODEX_HOME`. `catl hook ...` exits 0 on every path a hook can take (unknown name, bad input, error, panic) because Claude Code treats exit 2 as a block, and the written command ends in `|| true`.
- Each language analyzer depends on `atlas-core` alone and must never panic or hang on any input, nor overflow a 2 MiB stack (bound recursion with a depth cap or use an explicit stack). tree-sitter itself recurses in C, once per parse-stack node when it merges GLR versions (`` sql<a><a>…`x` ``) and once per tree level when it looks up the parent of a zero-width (MISSING) node, so the TS analyzer parses on a stack grown to 128 bytes per source byte (`stacker`) and never asks for the parent or siblings of a zero-width node.
- tree-sitter is vendored in `vendor/tree-sitter` (crates.io 0.27.0 plus the `code-atlas patch` in `src/stack.c`, applied through `[patch.crates-io]`). Upstream `ts_stack_pop_all` returns one slice per path through the parse stack, so a stack merged once per token (an unterminated `sql<a><a>…` at end of file) costs quadratic memory inside one call that no progress callback or `Deadline` can interrupt: 2.6 GiB at 64 KiB, killed at 2 MiB. The patch stops forking there once live iterators plus finished slices reach 64, which leaves such a parse linear (about 700 bytes per source byte for that input). Where a stack has more than 64 paths at the final accept, the chosen tree can differ from upstream's (seen as `type_arguments` versus `type_parameters` inside a top-level ERROR); files upstream failed on its budget can now yield facts, hence TS `ANALYZER_VERSION` 5. tree-sitter treats allocation as infallible (its default allocator aborts, callers never check for null), so a memory cap could only cancel a parse through the progress callback, which never runs inside that call; none is used. Upgrades follow `vendor/README.md` (the diff is `vendor/tree-sitter.patch`); cargo only warns when a `[patch]` stops matching, so `crates/atlas-lang-ts/tests/parse_memory.rs` is the guard. Workspace builds, `cargo install --path` and `cargo install --git` apply the patch; only a crate in another workspace depending on the analyzers gets upstream tree-sitter.
- Analysis time is bounded by `atlas_core::ParseBudget`: `2 s + 1 s per 100 KiB`, capped at 30 s, which is 31–55× the slowest legitimate file analysis (release). Budgets are charged in the analysing thread's CPU time (`CLOCK_THREAD_CPUTIME_ID` on Linux, Apple and FreeBSD; wall time elsewhere), so load, low QoS or SIGSTOP consume none of it, with a wall-clock backstop at 10× the budget. A `Deadline` therefore never leaves the thread that started it. One `Deadline` per file covers the tree-sitter parse (progress callback), Rust macro re-parses and the extraction walk. A parse whose furthest byte offset has not advanced for the stall limit (2 s of CPU; legitimate stalls stay under 60 ms) also overruns, which bounds the memory tree-sitter error recovery leaks while it loops (about 40 MB/s). Any overrun yields `FileFacts::failed` with `parse budget exceeded (<base budget ms> ms, <bytes> bytes)` whatever the phase, cause or retry escalation (logged via `tracing` instead), so the reason is deterministic; never partial facts. Reset a tree-sitter parser after a cancelled parse: a halted parse resumes on the next call and keeps its stack. tree-sitter error recovery can loop forever on small malformed inputs (regressions in `crates/atlas-lang-*/tests/hangs/`, stored as `.txt` so code-atlas never indexes them).

## Knowledge-model contracts

- Store writes take `(Owner, RunId, entities, edges, unresolved)`; owner and run are not fields on the DTOs.
- `EdgeId` discriminator is `""` by default: one edge per (kind, from, to) with merged evidence. Use a non-empty discriminator only when parallel edges mean different things, e.g. two `calls_endpoint` edges from one function to one endpoint with different auth headers (`"auth:bearer"`, `"auth:api-key"`).
- `FileFacts::symbol_keys()` returns keys positionally parallel to `symbols`. `~n` disambiguators are per file in source order, so reordering overloads changes keys (accepted). Cross-file key collisions (e.g. Rust `#[path]` aliasing) are handled by multi-owner entity semantics in the store.
- `Entity::from_symbol()` is the only way to turn a `SymbolFact` into an `Entity` (`Syntactic`, attrs under the `ATTR_*` names).
- `FileFacts.impls` holds one `ImplFact` per `impl` block, including empty marker impls and impls nested in fn bodies (`scope` = enclosing symbol); the resolver derives cross-file `implements` edges from it. `FileFacts.file_doc` carries file-level `//!` / `/*! */` docs.
- `ReferenceFact.origin` is `Syntax` by default. `MacroTokenScan` refs come from a token scan of macro bodies that do not parse as expressions; the resolver must cap their certainty at `heuristic`, never `resolved`.
- Fields added to existing IR structs use `#[serde(default, skip_serializing_if = ...)]` so serialized output is unchanged when they are empty or default.
- Unresolved refs are stored for display and debugging only; re-resolution re-analyzes the owner file, so the resolver never depends on stored refs alone.
- Scoping: env vars (`env:<repo>:<NAME>`), config keys, endpoints, auth schemes, permissions and jobs are repo-scoped. Events, queues and db tables are project-scoped, which assumes one logical database and one event bus per project.
- DB models: a table is an `EntityKey::DbTable`; a model class stays a symbol entity with its normal kind (class/struct) and gets a `maps_to_table` edge to the table. `EntityKind::DbModel` exists only for `Other` keys; detectors use the convention above.
- Client URL templates and base-URL composition are resolved by `atlas-link`; detectors record the raw `ArgSummary` pattern.
- TS member-chain references: `path` always starts with the chain head (`this`, `super`, a name, or `(expr)` for any other expression; computed members are `[expr]` segments) and `receiver` describes `path[0]`: `This`, `Identifier` for a non-local name, `TypeHint`/`Expr` for a local binding or expression. A head marked `TypeHint`/`Expr` is never resolved as an import or module symbol.
- TS tagged templates: a tag that is itself a call (`` db()`…` ``) yields a `Call` reference with path `["(<call text>)"]`, no receiver, the template as its only argument and the whole tagged template as span; the resolver treats the `(…)` head as `Dynamic`. tree-sitter-typescript 0.23 has no type arguments on a tag (`` sql<T[]>`…` `` is an error, `` sql<T>`…` `` a comparison), so when a TS/TSX tree has errors or a `>` comparison whose right operand is a template, the analyzer replaces each `<…>` that follows a non-keyword identifier (not `return`, `typeof`, …), `)` or `]` and precedes a template (whitespace allowed, as TypeScript reads it) with spaces, keeping newlines and every offset, and reparses under the same `Deadline`. Angles holding what no type can hold outside braces (a call such as `b()`, `x[0](1)` or `(f)(x)`, or `+`, `*`, `/`, `%` or a binary `-`) are never masked. The masked tree is kept only if every masked range lies between a `call_expression`'s function and its template argument, every ERROR/MISSING range of the masked tree lies inside one of the original tree, neither the error count nor the bytes under those nodes grow, and the error count drops or the comparison form was present; otherwise the original tree stands, all or nothing. Facts from a masked tree are read from the masked text, so they never contain the masked type arguments.
- `ReceiverHint::TypeHint` = declared type only (annotation, param type, struct literal, allowlisted newtype extractor such as axum `State(s): State<T>`), never inferred from a call such as `T::new()`; the resolver may infer from a constructor's signature with `heuristic` certainty.
- `ReceiverHint::Declared { type_text, binding }` (Rust) replaces `TypeHint` when the head is a param or annotated `let` whose declared type is a generic parameter in scope or a `Box`/`Arc`/`Rc` wrapper, because the `TypeHint` path would drop the bounds or the inner type. `type_text` is the whitespace-normalised declared type. A shadowing binding without an annotation is `Expr`. Bindings inside fn or impl items nested in a body keep `TypeHint`/`Expr`, because their references are attributed to the outer symbol, whose generics differ.
- `ReceiverHint::Chain(ReceiverChain { head, steps })` (Rust) replaces `Expr` on a `MethodCall` whose receiver is not a plain field chain but is a chain of at most 8 steps (`Field`, `Method`, `Try` for `?`, `Await`) over a head that is either a binding (`self`, a typed local or a name; `hint` as for `path[0]`, except that a param or annotated `let` is always `Declared` with its full type text, and an untyped local emits no chain) or a path call (`f(..)`, `T::new(..)`, `Enum::Variant(..)`; `args` holds each argument's declared type text when it is a typed binding, optionally behind `&`). `path` keeps the `(expr)` head. No chain is emitted inside items nested in a body, for a callee that is a local or starts with a generic parameter, or for any other receiver shape (index, deref, closure call, literal).
- Rust field accesses (reads and writes, not method callees) are `ValueRef`s whose `path` is the `self` or identifier head plus the field chain, with `receiver` describing `path[0]`; path `ValueRef`s have no receiver. An accessed tuple field (`.0`) or an expression head emits nothing, and at most 4 spans are kept per (symbol, path, receiver).
- Inside fn, impl or trait items nested in a body (attributed to the outer symbol), Rust `self` heads are `Expr("self")` and a `Self` path head is rewritten to `(Self)`, so the resolver never binds them to the outer impl: `(Self)` paths are `Dynamic`, and `self` receivers are unknown.
- `ReferenceFact.origin` = `MacroTokenScan` also covers macro arguments that only parse piece by piece, except for known expression-macro families (std format/assert, `tracing`/`log` level macros, `anyhow!`/`bail!`/`ensure!`), which keep `Syntax`.
- `NodeRef::Unresolved { path, from }` (detector output only): the engine resolves `path` in the owner file with `atlas-resolve::resolve_path_in_file`, scoped to `from`. The stored edge keeps the weaker of the detector's and the resolution's certainty; an unresolvable path drops the edge and is counted.
- TS detector paths `[T.., "prototype", m]` resolve `m` on the instance side of class or interface `T`, following `extends`; any other kind of `T` is NotFound. A static member is `[T, m]`. Rust detectors never emit this form.
- `test-mocks` emits `references` edges from test code to the mocked member, `heuristic(0.6, "jest-mock-member")`. Attrs: `mock` (`ATTR_MOCK`) is `replaced` for a `jest.fn()`/`vi.fn()` property, a `createMock`/`jest.Mocked` binding or a `mockImplementation`/`mockReturnValue`/`mockResolvedValue`/`mockRejectedValue`/`mockReturnThis` setup (also chained on `spyOn`), and `spied` otherwise; `mock_type` (`ATTR_MOCK_TYPE`) says how `T` was inferred; `mock_site` names the pattern. `bun:test` forms (`mock(...)` properties, `spyOn`, `mock.module`) apply only to bindings imported from `bun:test`. Block-scoped `const`/`let`/`var` named like a `bun:test` binding shadow it; function declarations, parameters and destructured locals do not. `mock.module(spec, factory)` is `replaced` with `mock_site = module` and rule `bun-mock-module`: one edge per name in an object-literal factory (`mock_type = module_export`, `Unresolved [name]`, so only names the test file itself imports resolve) and, for a relative specifier, one edge from the test scope to each candidate file key (`module_file`; the engine drops the nonexistent ones).
- Queries never treat an edge carrying `mock` (on the edge or any `site_attrs` entry) as production usage or as exercising its target, whatever its certainty: in `tests-for` only a mock edge on a test's own reached path yields `spies on it`/`mocks it`; a mock in its suite, file or called helper adds a note to a real reach, or alone yields the hedged `its scope mocks it` naming that scope. A `mock.module` edge (`mock_site = module`, to an export or to the module's file) replaces the module for every importer in the test process and Bun's `mock.restore()` does not undo it (bun.sh/docs/test/mocks), so wherever in a test file the call sits, every test in that file, whatever its reach (direct call, import, `covers_file`), is `its scope mocks it` with the file noted, never a real reach; `impact` lists a test that reaches the target only through a mock edge among relevant tests, not among dependents.
- Drizzle (`db` detector, files importing `drizzle-orm`): a table constructor bound to a constant gives `DbTable` plus `maps_to_table` (`syntactic`, `schema.table` for `pgSchema`). Query-builder calls give `reads_table`/`writes_table` edges (`heuristic 0.6`) whose target is `Unresolved` to the table constant, not the `DbTable`. `impact` therefore reaches those readers only transitively through the constant's references and `maps_to_table`, and table-centric listings (`patterns db`, `explain table:...`) do not show Drizzle accesses yet.
- Dangling targets: the engine drops detector edges whose `NodeRef::Key` target entity does not exist after the run (e.g. `covers_file` to a guessed sibling file) and counts them. Detector edges may repeat (kind, from, to) with different spans; the engine merges them into one edge with one evidence per span.
- Decorator routes: `http-endpoints-nest` is the built-in instance of the table-driven engine in `atlas-detect` (`detectors/routes.rs`, `DecoratorFamily`); no other family is compiled in. Declared families come from `<config dir>/detectors/<name>.toml` (parsed strictly by `DecoratorFamily::parse`; unknown keys warn; a file with an invalid name, or invalid content in a family no project enables, is skipped with a warning; invalid content in an enabled family fails the registry load naming the file and key) and are enabled by the fact key `detect.route_families` (`config.toml [defaults.detect]`, `projects.toml [project.settings.detect]`, or added by a repo's `.code-atlas.toml [detect]`; never env or flags). The registry resolves them into `ProjectSettings.detect` (`route_families` = effective names, `families` = definitions found). They run as one detector, `http-endpoints-declared`, registered only when a project enables a declared family; its producer version is a digest of `DECLARED_ROUTES_VERSION` and the definitions. A decorator matches only when imported from a family package (named, aliased or namespace); there are no name-only matches. Certainty as for Nest; endpoints carry `framework = <family name>`. A family's global prefix is `other:http_family_prefix:<repo>:<family>:<prefix>` (Nest keeps `http_global_prefix` with the bare prefix), and `atlas-link` composes `http_global_prefix` only onto `nestjs` endpoints and a family prefix only onto that family's endpoints.
- Typed clients: `http-clients` also matches `openapi-fetch` (`GET`..`OPTIONS` on a binding initialised in the same file by `createClient` imported from `openapi-fetch`). A family file's `[client]` section (a file may hold only that section) declares other client shapes, run by `http-clients-declared`, registered only when an enabled family has one; its producer version is a digest of `DECLARED_CLIENTS_VERSION` and the client sections, and the section enters the fingerprint through the family digest (a family without one keeps its digest). A call matches only on a receiver anchored on an import from a listed module specifier or an in-repo file matching a listed glob (relative specifiers resolved against the importing file), or on a local initialised by a listed factory import; no name-only matches, no cross-file following otherwise. Detectors rewrite whole `{name}` (OpenAPI) or `:name` (Express) path segments to `{}` and keep the written path in `path_template`; `atlas-link` parses no other placeholder. `makes_request` attrs `types_module`/`types_path` (the import of `createClient<T>`'s type argument) and `target_package` (declared) feed placement. An exported constant initialised by openapi-fetch `createClient` is recorded as `other:typed_client:<repo>:<path>#<export>` (attrs `modules` = path without extension plus the directory for `index` files, `export`, `base`, `base_source`, types); a declared `files` client imported by a relative specifier records `client_module`/`client_export`, and `atlas-link` joins the two (never the detector). Family names that equal a built-in client `library` (`fetch`, `axios`, `nest_http`, `openapi-fetch`, `reqwest`) are refused, because `status` counts client calls per `library`.
- Monorepo placement (`atlas-link`): packages are the nearest manifest of a file (from file-owned `Package` entities whose `manifest` attr is their owner path). Endpoint and ClientCall keys never include a package; the pass annotates `packages` (every asserting file's package; a composed route only those it shares with its prefix; only in repos with more than one manifest) instead, composes a global prefix onto an endpoint only from prefixes of the endpoint's own packages when one exists (otherwise every prefix of the repo, as before), and restricts a call's candidates to one package in this order when that package has a candidate: types package, `target_package`, the caller's package for a relative URL. `calls_endpoint` records `client_package`, `endpoint_packages`, `target_package`, `package_rule`. A route two apps expose stays one endpoint with both `exposes_endpoint` edges.
- Detector-only edge kinds: `makes_request` (caller → `ClientCall`), `implements_auth` (guard/strategy/middleware → `AuthScheme`), `requires_guard` (endpoint → guard, usually `Unresolved`, attrs `level`/`order`). `atlas-link` consumes them to derive `calls_endpoint`, `supports_auth` and `uses_auth`.
- Endpoint certainty covers the route and mount chain only; handler resolution lives on the `exposes_endpoint` edge, which is dropped if its `Unresolved` handler cannot be resolved. Keys never include a Nest global prefix (emitted as `other:http_global_prefix:<repo>:<prefix>`); routes on a router not mounted in the same file carry `route_scope = "router_relative"` (Express adds `router`), and cross-file mounts are custom `mounts` edges to the mounted router (attrs `mount_prefix`, `mounted_on`, `mounted_on_scope`).
- Detector attrs for `atlas-link`/queries: `makes_request` edges carry per-call-site `base_source`, `auth_hint`, `auth_hint_source`; `new Sdk({ auth: { type } })` yields a `references` edge to the class with `uses_auth_option`; composite guards emit `references` edges with `delegates_to`; env reads in test code carry `in_test = true`. Fully dynamic client URLs produce no `ClientCall`, only an `http.dynamic_url` diagnostic with the call span.

## Conventions

- Rust 2024, 2-space indent, 180 columns (`rustfmt.toml`).
- No comments unless the code cannot say it (external behaviour, non-obvious constraint, a bug the shape prevents). No doc blocks restating names, no dead code, no TODOs.
- Typed errors via `thiserror` per crate; no `unwrap`/`expect` on fallible runtime paths outside tests.
- No `println!`/`eprintln!` in library code; use `tracing` with structured fields.
- Model states as enums / discriminated unions, never parallel booleans. Prefer early returns.
- Tests are named `should_*` and assert exact values.
- New third-party dependencies go in `[workspace.dependencies]` and need a stated justification.

## Engine contracts (`atlas-engine`)

### Freshness

- `Engine::ensure_fresh()` is the barrier every query runs first. It stat-scans every repo and runs an incremental update when anything changed. With a healthy watcher it skips the scan only if no event arrived since the last scan and that scan is younger than `full_scan_interval` (60 s). Events mark the watcher dirty inside the notify callback. A watcher error, overflow or rescan event forces the next barrier to scan, and a dead worker or channel makes every barrier scan. Residual risk: an edit whose event has not been delivered yet.
- The barrier returns `FreshnessReport::Fresh(header)` or `Degraded { failed_files, reason }`, and queries must surface `Degraded`. It is degraded in these cases:
  - the update failed (store error, lock timeout, a panic inside the update);
  - a file could not be read or analysed during this update;
  - a project pass failed or panicked (the run is `partial`);
  - a repo root is unavailable;
  - another engine adopted a different project configuration.

  Facts of failed or removed files are deleted, never kept stale. `header.files_failed_analysis` keeps counting files that failed in earlier runs.
  A failed file is analysed again only when its content, package context, analyzer or detector versions change, or on a full index. Budget failures are the exception, because they depend on machine load:
  - After the parallel pass a run re-analyses its budget-failed files one at a time at 2× the budget, but only when at most `available_parallelism` files failed (more signals load, so all of them wait for the schedule), and it stops once the pass has run longer than 2 base budgets of the largest failed file.
  - Files that still fail get `{attempts, retry_at_ms}` in `engine:meta` (never in file-owned facts). A barrier with a due retry runs even without a file change and analyses the file at 4×, 8×, then 16× the budget (capped at 30 s; the stall limit at 4×) after `EngineOptions::budget_retry_backoff` (1 min, 10 min, 1 h). After that it waits for a change. A barrier takes at most `available_parallelism` due files, oldest first; the rest stay due. A content, package context or version change (or a full index) restarts the sequence.
  - Worst-case latency added to one query on an idle machine: a run that first sees K hang files spends about `ceil(K / threads) × 2 s` in the parallel pass plus at most 2 base budgets of the largest failed file (one serial retry may finish past that, up to 4×) in the serial pass, so about 6–10 s for small files whatever K is. A due barrier analyses at most one file per thread in parallel: a hang stops at its 8 s stall limit, a file that keeps advancing at its escalated budget (at most 30 s of CPU). Under starvation the wall time grows with the slowdown, up to the 10× backstop.
  - `status` lists each budget-failed file with its next retry. Only a run that analysed a failed file reports `Degraded`; other barriers are `Fresh` and keep counting it.
- Scans pass the start time of the scan that produced the stored stamps as `previous_scan_ns` (persisted per repo in the `engine:meta` blob); an unknown time hashes everything.
- Concurrency:
  - Barriers in one process are single-flight: a caller joins only a flight launched after it arrived (ticket `launched + 1`), so it never receives a scan that started before its call. Queries run after the barrier on the store's read-connection pool, outside the engine lock; one query uses one read transaction. `Engine::skip_barrier` / `QueryEngine::without_barrier` exist for benchmarks only and must never be reachable from the CLI or MCP.
  - Across processes, `<db>.index.lock` is held for a whole run, and the store write lock only per persist batch. After taking the index lock, the engine always re-reads the persisted generation (the last finished run in `engine:meta`). If it moved, the engine reloads its state and re-plans from a fresh scan.
  - The `engine:dirty` blob exists while a run is in flight. A barrier that sees it waits for the index lock. A dirty marker found while holding the lock means a crashed run: the engine reloads (ignoring the persisted similarity index), marks the orphaned `barrier`/`index`/`edit` runs `failed`, recomputes SCIP lag, and the next run re-resolves every file. If dependency rounds do not converge, the run stays `partial` and keeps the dirty marker, so the next run re-resolves everything.
- `Engine::write_then_refresh(files, write)` holds the engine mutex and `<db>.index.lock` (barrier order) across `write` and an incremental refresh run (trigger `edit`), so no barrier in any process indexes a half-applied write. The refresh always scans and re-hashes every path in `files` whatever its stat says (mtime-preserving writers, clock skew), also when `write` errors or panics (the panic resumes after the locks are released). It returns `Err` without calling `write` only for an unknown repo, a lock timeout or a failed sync; `write` must not call back into the engine.
  - `<db>.edit.lock` (atlas-edit) is taken only inside the `write` closure, so the order is engine mutex → index lock → edit lock. Taking the edit lock first and then running a barrier deadlocks.
  - A worktree overlay edits with its base project's `<base db>.edit.lock` (`IdeOptions::in_overlay`), because its repos outside the worktree are the base's checkouts: the order there is overlay engine mutex → overlay index lock → base edit lock. A base process never waits on an overlay lock (cleanup only try-locks it), so the order stays acyclic. `EditLock::open` creates the lock file's directory, so an overlay of a never-indexed project can edit.
  - Another process's barrier waits on the index lock for the whole write plus refresh, and returns `Degraded` (lock timeout) if that outlasts `lock_timeout`.
- Project configuration: `engine:project` holds a fingerprint of the repos (name, path, include/exclude, languages), `max_file_bytes` and the store `SCHEMA_VERSION`, so an engine built for another schema degrades instead of writing. When `detect.route_families` is non-empty, the names and a digest of the resolved definitions are added (a project without families keeps its fingerprint), so a CLI and a long-lived MCP server holding different family definitions do not re-analyse each other's artifacts; `reload_project` rebuilds the toolchain when `settings.detect` changed. The fingerprint is computed from the effective project the registry resolves (built-in → `config.toml` → `projects.toml` → repo `.code-atlas.toml`); environment variables and flags never set these fact keys. `Engine::open` and `Engine::reload_project` adopt their configuration. Any other engine whose fingerprint differs reports `Degraded("project configuration changed; reopen the engine")` and neither purges nor indexes. Long-lived servers must call `reload_project` when the registry changes. Always open an engine with the full registry `Project`: opening with a subset adopts it and purges every other repo. The transaction that begins a run records the configured repos in `engine:repos` before any file owner is written. On the next run, repos from `engine:repos`, Repository entities and meta that are absent from the adopted configuration are purged, even when the previous run crashed. Stale entries are cleared only after a run finishes.
- SCIP and LLM enrichment never run inside the barrier. Every file owner written by a run, whether its content changed or it was only re-resolved, loses its `scip:` owner. It is added to `engine:scip.lagging` and stamped in `dropped_in` in the same transaction, whether or not SCIP has run, and `header.scip` reports the lag once SCIP has run.
- The similarity index is updated in memory every run and persisted on `Engine` drop, after `similarity_persist_idle` in the watcher, or via `persist_similarity()`. Long-lived processes, the MCP server in particular, must call `persist_similarity()` on SIGTERM/SIGINT, because signals skip drops. The blob is stamped with its generation; a stale or missing blob is rebuilt from the artifacts at open.
- `Engine::scip` syncs the generation before planning. It ingests a file only when the stored artifact, the hash the indexer was given and the disk agree; any other file stays lagging. Before writing `scip:` owners under the index lock, it re-checks the hash in the files table. If the persisted generation moved since the jobs were built, it also re-reads the repo's graph fingerprint and the lag set: a changed fingerprint leaves the whole package lagging, and a file whose `dropped_in` stamp (the run that last dropped its `scip:` owner) differs from the job's snapshot is skipped. Deleted files are removed from `engine:scip.lagging` when the run removes them, and ingest drops every lagging entry without a file record.
- After dependency rounds, a run also drops every `scip:` owner with an edge into an entity the run removed (dependency tracking cannot see edges only SCIP produced) and marks its file lagging with `dropped_in`, like a re-resolved file.
- SCIP indexing units: a Cargo workspace member is indexed with its whole workspace (one rust-analyzer run at the `[workspace]` root, `package_dir` = workspace dir), so cross-crate references map to project definitions; standalone crates and npm packages run per package. With one workspace-wide index every member is re-ingested on each run; this is safe because each file is still gated on its own hash, its `dropped_in` stamp and an unchanged `(len, mtime)` between indexer start and ingest (catches A→B→A edits), and a file that changed mid-run contributes no definitions, so references into it are dropped rather than mis-mapped. The index is decoded and mapped outside the engine mutex; only the final write holds it with the index lock.
- Automatic SCIP: when `EngineOptions::auto_scip` has indexers and a watcher runs, the watcher schedules `Engine::scip` (ledger trigger `scip-auto`) on its own thread once `scip.enabled` is set (opt-in, default off: `catl project config <p> --scip on`; explicit `scip` ignores the setting), no file event arrived for `scip.debounce_secs`, no refresh is pending, and lagging files exist that a ready indexer covers. It never blocks barriers and never marks them `Degraded`. One run at a time per project: `<db>.scip.lock` is held by every SCIP run (explicit runs wait for it, automatic runs skip when it is busy) and is what `status` probes for "in progress". After an attempt it waits for the persisted generation to move before trying again. A package whose indexer failed or timed out is skipped while its inputs (file hashes plus graph fingerprint) are unchanged, for at most `AutoScipOptions::failure_retry` (1 h). The hold fingerprint covers parsed manifests and tsconfigs through the graph fingerprint but not lockfiles, `rust-toolchain*` or `.cargo/config*`, which the cache key does include: fixing a failure by changing only those waits for the hold to expire or a source edit (or a restart). When the backlog is empty or entirely held, the generation is recorded as attempted so the scheduler does not rebuild jobs every tick. A run cancelled at any point is recorded `partial`. An `Unavailable` indexer warns once per process and pauses for `AutoScipOptions::unavailable_retry` (1 h) or until restart. Dropping the `WatchHandle` cancels the run (the indexer process group is killed) and joins it. The last automatic run and backoffs are persisted in `engine:scip.auto`; `status` hides backoffs past their `retry_at_ms`.

### Worktree overlays

- Binding goes through `atlas_engine::bind_project` (CLI `Context::bound`, once per command; MCP `Session::open`), never `Registry::resolve` alone, wherever an engine is opened. `[worktrees] mode` (`config.toml` only): `overlay` (default), `main` (registry binding: caveat, edits refused) or `off` (`ProjectError::WorktreeIgnored`; CLI exit 2, MCP unbound).
- `Registry::derive_overlay` maps a `Binding::Worktree` to an overlay only when the worktree shares its git common dir with the checkout holding the registered repo: every repo registered at or below that checkout's root moves to the same relative path in the worktree, which must canonicalise to itself (no symlinked or missing directory); other repos keep their paths. The project is re-resolved through the config layers with the worktree's repo files. The overlay's `ProjectName` is `<base>.<worktree slug>-<8 hex of blake3(base, canonical worktree root)>`; its label is `<base>@<worktree dir>`. Anything else (enclosing parent folder, unresolvable `.git`, missing directory, a failed seed or lock timeout) falls back to the registry binding with its refusal plus a warning; it never edits through the base project.
- Overlay databases live under `AtlasHome::overlay_home()` (`<data>/_worktrees/<name>/atlas.db`; a project name cannot start with `_`), recorded in `<data>/worktrees.json` (versioned; a newer version is an error, never overwritten blindly). `<data>/_worktrees/<name>.lock` is shared by every process using the overlay for its lifetime and exclusive while seeding or collecting. It is never deleted (unlinking a flock file lets two holders in); cleanup deletes only the overlay database's own lock files inside `_worktrees/<name>/` (with the directory), while holding `<name>.lock` exclusively.
- Seeding (`Overlays::acquire` → `seed_overlay`): under the exclusive overlay lock, write the record, refuse (`InsufficientSpace`, so the registry binding applies) unless the overlay directory's filesystem has at least twice the base database plus its WAL free, then `atlas_store::backup_database` copies the base under `<base db>.index.lock` into `atlas.db.seeding`, `forget_scan_times` clears `scan_started_ns` of the remapped repos (so every stamp is racy and re-hashed), the store is closed, a non-empty leftover `-wal`/`-journal` refuses the install, and the staging file is fsynced and renamed into place. A final `atlas.db` therefore means a complete seed; staging leftovers are removed before and after every seed. A base without a database seeds an empty store and creates no database under the base's data directory; the first overlay edit creates that directory for `<base db>.edit.lock` only.
- An overlay engine must only ever be reloaded with a re-derived overlay project (`current_overlay`), never with the base project; `Engine::reload_project` rejects another name, and a session whose overlay can no longer be derived fails its tools (`OverlayGone`).
- Reporting: in an overlay, edit output marks each changed file outside the worktree's repos with its checkout (`ChangedFile::outside_worktree`); `status` (CLI and MCP) adds the overlay line (label, base, repos from the worktree, seed age, SCIP lag) and an `overlay` JSON field, and sets `StatusAnswer::settings_project` to the base, so hints name a project `project config` knows.
- GC (`collect_garbage_if_due`, at most hourly, after an acquire and from every command bound directly to a registered project) removes an overlay only while it can take its lock exclusively without waiting and the re-read record is still stale (worktree gone, base unregistered, or unused for `gc_after_days`); it deletes only `overlays_dir()/<name>` and the record, in that order.

### Incremental ≡ full

- A file owner's facts are a pure function of its persisted artifact (`artifact:<repo>:<path>` blob: `FileFacts`, detector outputs, package context, generated flag), the symbol table, and the set of entities asserted by file owners. Never put run ids, timings or absolute paths into file- or pass-owned facts.
- The re-resolve set is the changed files, plus resolver relocations and `affected_files`, plus files whose detector `Key` targets appeared or disappeared, plus the safety nets `owners_referencing` (collected ids) and `unresolved_by_names` (created symbols). Any package-graph change re-resolves every file of the project.
- A detector `Key` target exists only if a file owner (including manifest owners) asserts it. Entities owned by project passes or SCIP never keep a detector edge alive.
- `renamed_from` edges (owner `Project { pass: "lineage" }`) are history and cannot be derived from the tree; digest comparisons import that owner first.
  - Identical bodies need at least 12 tokens. Across files that are not renamed, they need 30.
  - Bodies under 30 tokens whose names share no meaningful token are capped at confidence 0.6.
  - Inferred facts migrate only for lineage with confidence ≥ 0.85.
- `tests/incremental_equivalence.rs` and `tests/regressions.rs` (seeded random edit sequences and batches against a fresh full index) must keep passing.
- Any change to a producer's output must bump that producer's version (and its pin); the engine re-analyses or re-resolves on mismatch. Producers and their pins (`tests/version_pin.rs`):
  - the analyzers (`ANALYZER_VERSION`, re-analyses that language);
  - each detector (its `detector!` line; the engine compares the whole detector list, so one bump re-analyses every file); `http-endpoints-declared` is pinned separately as `DECLARED_ROUTES_VERSION` over the invented family in `atlas-detect/tests/family-corpus/` (`tests/declared_routes.rs`), which the main detector pin does not read, and the link pin also runs `atlas-engine/tests/pin-corpus/link-family/` with that kind of family enabled; the shared engine (`detectors/routes.rs`) is covered by both the Nest pin and that pin; `http-clients-declared` is pinned as `DECLARED_CLIENTS_VERSION` over `family-corpus/books-web/` with `family-corpus/acme-books.toml` (`tests/typed_clients.rs`), and the link pin also runs `atlas-engine/tests/pin-corpus/link-monorepo/` (several apps in one repo, `openapi-fetch` and a declared client with `target_package`);
  - the resolver (`RESOLVER_VERSION`, re-resolves every file);
  - project passes (`ProjectPass::version`: `STRUCTURE_VERSION`, `atlas_link::LINK_VERSION`; `engine:meta` stores `pass_versions`, and a mismatch triggers a run that re-runs the passes only). Their pin is in `atlas-engine`.

  A pin is `(version, inputs digest, output digest)` over `fixtures/` plus the crate's `tests/pin-corpus/` (resolver, detectors). Inputs cover only what the producer reads (language files, manifests, upstream facts), so eval ground truth and READMEs never trip a pin; a changed inputs digest only needs a re-pin. `.gitattributes` keeps fixtures and corpora byte-exact.

### `ProjectPass` (for `atlas-link` and later passes)

- `trait ProjectPass { fn name(&self) -> &'static str; fn version(&self) -> u32 { 1 } fn run(&self, tx: &ReadTx<'_>, context: &PassContext<'_>) -> Result<PassOutput, PassError>; }`, with `PassOutput { entities, edges }`. `structure` and `link` are built in; extra passes go through `EngineOptions::passes`; every engine that opens a database must register the same passes.
- Passes run on every index run, after all file and manifest owners are committed: `structure` and `link` first, then the registered passes in order. Each output replaces the owner `Project { pass: name }` wholesale.
- A pass must be a deterministic function of file-owned facts, `PassContext` (project, package graphs, manifest hashes) and earlier passes. It must not read its own previous output or the `lineage` and `scip:*` owners.
- An error or panic in a pass removes its facts and makes the run partial. The names `repos`, `structure`, `link`, `lineage` and the prefix `scip:` are reserved, and `Engine::open` rejects them and duplicate names.
