# atlas-store contracts

- Edge targets may be dangling; the engine re-resolves via `owners_referencing` and drops dangling detector edges.
- Run lifetime: `begin_run` and `finish_run` go in their own write transactions, and every write transaction in between calls `resume_run(id)`, because the active run belongs to one `WriteTx`. `begin_run` fails with `RunAlreadyActive` when a run is already active in that transaction, and so does `resume_run` with a different id.
- `replace_owner` / `remove_owner` run inside a savepoint: on error they leave no partial state, even when the caller swallows the error and commits.
- Re-entering the store from a thread that already holds one of its transactions fails with `StoreError::Reentrant`; use the `ReadTx`/`WriteTx` already in hand. A `read` inside a file-backed `write` is allowed and sees the pre-write snapshot.
- Merged view of an entity or edge: certainty, kind-specific fields and (for edges) the sorted, deduplicated evidence come from the winning assertion (strongest certainty, ties to the smallest `Owner`). `attrs` are the union of every assertion's attrs: on a key conflict the winner's value wins, then the smallest `Owner` in `Ord` order. The union never changes certainty and does not depend on write order; `fact_set_digest` hashes the merged view. `entity_assertions` / `edge_assertions` return the unmerged facts.
- `entity_with_sources` / `edge_with_sources` return the merged fact plus `attr_sources`: for every attr, the `Owner` and `Certainty` of the assertion whose value was kept. Renderers MUST tag each attr with its own source certainty, never with the merged entity's: a heuristic link-pass attr on a syntactic entity is still heuristic.
- Assertion rows (`entity_owners`, `edge_owners`, `unresolved_refs`) hold a compact encoding, not the core serde JSON. For file owners it elides values equal to the owner: evidence and unresolved `repo`/`path`, and evidence `content_hash` equal to `owners.content_hash` (the most common hash of evidence located in the owner file). Reads hydrate every row, so all read APIs and `fact_set_digest` return exactly what was written, and a body edit that keeps spans rewrites no row. Only the store decodes `data` columns. Rows in the core serde shape (schema v1) are accepted on read forever, or until a later schema drops them: a pre-v2 binary that re-adopts the project (its `watch` or MCP reload) writes them into v2 tables. The decoders try the compact shape first and fall back to core serde; the two share no required key, so each row parses as exactly one of them. A legacy row whose id disagrees with its row id is `Corrupt`. Hydrated legacy and compact rows of one fact are identical (same digest), and the next `replace_owner` of that owner rewrites them compactly because the bytes differ (counted as `changed`).
- `PreparedOwner::new` validates and encodes an owner's facts without touching SQLite; build it off the writer thread and apply it with `replace_prepared`.
- `bulk_writes()` raises the WAL auto-checkpoint threshold until `finish()` (or drop), which runs a non-blocking `TRUNCATE` checkpoint. On a store that holds no facts, `defer_indexes_while_empty` drops the secondary fact indexes (name, kind, file, src, dst, unresolved name); on a store that holds facts it rebuilds any that are missing. Call `restore_indexes` before any query that filters on them. Only a bulk load running under the engine's index lock may leave them missing, so the engine rebuilds missing indexes in the transaction that begins each run, and `Store::open` rebuilds them only when it can take `<db>.index.lock` without waiting (otherwise the indexer that holds it restores them).
- The defer/restore DDL transactions are the one exception to "every write transaction in a run calls `resume_run`": they write no facts or run rows.
- Run fact deltas (`run_fact_deltas`, `FactDelta`) count rewritten assertion rows, not semantically changed facts: a body edit that only changes the file hash shows `edges.changed = 0`, and a span shift counts as a change.
- Schema migrations run under `<db>.index.lock` and the writer lock, so an older binary's in-flight run finishes first. Every upgrade of an existing database overwrites `PROJECT_FINGERPRINT_BLOB` (`engine:project`) with a sentinel in the migration transaction, and the engine fingerprint includes `SCHEMA_VERSION`, so an older engine still open reports `Degraded` and stops indexing even if it wins the index lock before a current engine adopts the project. Never delete that blob: a missing fingerprint passes the engine's check. A legacy row that cannot be decoded fails with `StoreError::Migration` (delete the database and re-index). Migrated databases keep their file size until a fresh index or a manual `VACUUM`.
- Each reader connection's page cache is `min(16 MiB, 512 MiB / readers)`. `mmap_size` stays off: on the 1M impact scenario it raised peak RSS by 190–530 MB with no latency gain.
