# Languages and frameworks

Supported file extensions: `rs`; `ts mts cts`; `tsx`; `js mjs cjs`; `jsx` (`Language::from_extension`). `.d.ts` declaration files are recognised as such. Analyzers are tree-sitter based (`tree-sitter-rust`, `tree-sitter-typescript`, `tree-sitter-javascript`). A repo may restrict languages with `languages` in `projects.toml`.

## Depth per language

| Capability | Rust | TypeScript / JavaScript (TSX, JSX) |
|---|---|---|
| Symbols | fn, method, struct, enum, variant, trait, type alias, const/static, field, module, macro (`macro_rules!`), tests | function, method, class, interface, type alias, enum, const/variable, field, namespace, tests and suites |
| Signatures, docs, visibility, modifiers, attributes | yes (`//!` file docs too) | yes (decorators with literal arguments recorded) |
| Imports and exports | `use` trees, globs, `extern crate`, `mod` declarations, `#[path]`, inline modules | ESM `import`/`export`, `export *`, re-export chains, default exports, `require()` as import, barrel files |
| Module system | module tree from each Cargo target root (lib, bins, tests, examples, benches, build script) with rustc mod-rs rules; `cfg`-gated files keep their path and record the cfg text | relative paths, `tsconfig` `paths`/`baseUrl`, package `exports`, workspace packages, unbuilt entries mapped to sources through tsconfig `outDir`/`rootDir` (exact), otherwise dist-to-src mapping (heuristic 0.85 per hop) |
| Call resolution | path calls, method calls on typed receivers (declared types, params, annotated lets, struct literals, newtype extractors), `Self::`, trait-method calls via bounds, `Box`/`Arc`/`Rc` wrappers, field accesses (reads and writes) | scope-based (shadowing aware), namespace-aware (value vs type), `this`/`super`, instance vs static members, overloads resolve to the implementation signature, JSX elements, decorators |
| Dispatch | `dyn Trait` and interface candidates heuristic 0.3; generic bounds resolve to the trait method | interface and subclass override candidates heuristic 0.3 |
| Unresolved | untyped `let x = T::new()` receivers, expression chains, macro-generated names, fn-local items, `self` in items nested in bodies (`Unsupported`) | computed members (`a[b]()`), dynamic `require`/`import()`, rebound `this` and `this: T` annotations inside classes (`Unsupported`, no candidates; outside classes name-only heuristic candidates) |
| Parse-error tolerance | partial parse: facts around errors extracted, up to 8 errors reported | same |
| Similarity and lineage | body fingerprints (normalized token streams, capped at 4,096 tokens) | same |
| Tests | `#[test]`, `rstest`, `test_case`, `<framework>::test` attributes (for example `tokio::test`); `#[cfg(test)]` modules; `tests/` integration directory | `describe`/`it`/`test` calls; frameworks identified: `jest` (globals and `@jest/globals`), `vitest`, `mocha`; `node:test` and `bun:test` recognised as unknown framework; `.spec.`/`.test.` files and `__tests__`/`test`/`tests` directories |
| Compiler-grade verification | rust-analyzer SCIP | scip-typescript SCIP |
| Exact operations (live, not stored) | rust-analyzer (PATH or `rustup which`; never downloaded) | typescript-language-server 5.x with TypeScript below 7 (installed, or fetched through `npx` when downloads are on); TypeScript 7 has no `tsserver` and is refused |

`atlas-lang-rust` and `atlas-lang-ts` must never panic on any input; a failure becomes a failed-file record, not a crash. Details of resolver certainty rules are in [knowledge model](knowledge-model.md#certainty-classes) and `crates/atlas-resolve/CLAUDE.md`.

## Frameworks and detectors

Eleven detectors run on every analyzed file (`DetectorRegistry::default`). Each emits entities and edges with its own certainty, plus diagnostics (for example `route-dynamic`, `http.dynamic_url`).

| Detector | Detects | Libraries and conventions | Tested on fixtures |
|---|---|---|---|
| `http-endpoints-nest` | endpoints, controller prefixes, global prefix, guards | NestJS (`@Controller`, `@Get/@Post/@Put/@Patch/@Delete/@All/@Head/@Options`, `@UseGuards`, permission decorators whose name ends in `Permission`, `Role` or `Scope`, e.g. `@RequirePermission`); the built-in instance of the decorator-routes engine below | acme-api |
| `http-endpoints-express` | endpoints, router mounting, mounts across files | `express`, `fastify`, `koa-router`, `@koa/router` registration calls (`get post put patch delete del head options all`) | globex-api, computed-routes-ts (Express); Fastify and Koa in detector unit tests only |
| `http-endpoints-axum` | endpoints, `.nest` composition | `axum` builders; `actix_web` and `rocket` route attributes | acme-billing (axum); actix-web and Rocket in unit tests only |
| `http-clients` | outgoing requests: method, URL pattern, base-URL source, auth hints, headers | global `fetch`, `axios` (methods and config form), Nest `HttpService`, Rust `reqwest` (including `bearer_auth`, `basic_auth`); `new Sdk({ auth })` options | acme-sdk, acme-web, acme-billing |
| `auth` | auth schemes and guards | Nest guards, `@nestjs/passport` (`AuthGuard`, `PassportStrategy`, strategies `passport-jwt` etc.), Nest and Express middleware, axum middleware, Rust extractors; header and cookie reads (`Authorization`, `x-api-key`, cookies) classify `bearer`, `api_key`, `basic`, `session_cookie` | acme-api |
| `config-env` | env var and config reads | `process.env.X`, destructuring, `import.meta.env`, `std::env::var`/`var_os`, `dotenvy`, `ConfigService.get/getOrThrow` | acme, globex |
| `tests` | test to file coverage | naming conventions (`foo.spec.ts` covers `foo.ts`; Rust `tests/` and `_test.rs`), `#[cfg(test)]` modules | acme |
| `test-mocks` | jest, vitest and `bun:test` mocks and spies in test code, linked to the mocked class or interface member | `jest.fn()`/`vi.fn()` properties, `createMock`/`jest.Mocked` bindings, `spyOn` and `mockImplementation`-style setups; edges are `heuristic 0.60` and carry `mock = replaced` or `spied`. `mock(...)` properties, bare or namespaced `spyOn` and `mock.module(specifier, factory)` count only when bound from `bun:test` (named, aliased or namespace import); a local `mock`/`spyOn` never matches, including a block-scoped `const`/`let`/`var` that shadows the import (function declarations, parameters and destructured locals do not shadow). `mock.module` emits `replaced` edges (`mock_site = module`) from the test scope to each name in an object-literal factory (`mock_type = module_export`, resolved through the test's own imports) and to the candidate files of a relative specifier (`module_file`; candidates that do not exist are dropped); a non-literal specifier yields the `mock.dynamic_module` diagnostic. Module mocks in `bunfig` preload files are not attributed to the tests they affect. Assignment mocks (`x.m = jest.fn()`) and `mock<T>(...)` type arguments from `bun:test` are not detected | unit tests and two real repositories (review) |
| `events` (experimental) | publishers and subscribers | `EventEmitter`/`EventEmitter2`, receivers named like a bus (`events emitter bus broker queue producer consumer pubsub`) calling `emit publish send` / `on once subscribe listen`; `@OnEvent` from `@nestjs/event-emitter`; Kafka-style `topic` options | acme, globex |
| `jobs` (experimental) | scheduled jobs | `@nestjs/schedule` (`@Cron`, `@Interval`, `@Timeout`), `node-cron`/`cron` `schedule`, top-level `setInterval`, `tokio_cron_scheduler::Job` | unit tests |
| `db` (experimental) | tables, models, reads and writes | TypeORM `@Entity`, `sequelize-typescript` `@Table`, Prisma client model calls, SQL string literals (`select insert update delete with merge replace`), `sqlx` macros and `query_as`-style calls; Drizzle (files importing `drizzle-orm`): `pgTable`/`mysqlTable`/`sqliteTable` (named, aliased or namespace import) and `pgSchema(...).table(...)` with a literal name give a table (`schema.table` when schema-qualified) and a `maps_to_table` edge from the declaring constant, while `db.select().from(t)` (and joins), `db.query.<t>.findMany/findFirst` and `db.insert/update/delete(t)` on a receiver named like a database handle give `reads_table`/`writes_table` edges (`heuristic 0.60`) to the table constant, resolved through the file's imports. The access edges target the table constant, not the table: `impact` reaches them only transitively through the constant, and `patterns db` and `explain table:...` do not list Drizzle accesses yet. The receiver must be named `db`, `tx`, `trx`, `txn`, `transaction`, `database`, or start or end with `db`, or contain `drizzle` (`client`, `conn` and `orm` are missed), and relational `db.query.<t>` needs `<t>` imported in the same file. `pgTableCreator` and non-literal names are not analysed | acme (TypeORM), unit tests |

### Declared route families

The NestJS detector is one instance of a table-driven decorator-routes engine. Any other decorator framework can be described in a family file and enabled per project; Code Atlas compiles in no family except NestJS. A declared family runs as the detector `http-endpoints-declared`, which exists only in projects that enable at least one family. See [operations](operations.md#route-families) for the file format and how to enable one.

- **What it reads.** Controller decorators on classes and their path (an argument position, or a key of an options-object argument), route decorators on methods mapped to an HTTP method, guard decorators (each argument becomes a `requires_guard` edge with `level` and `order`, as for `@UseGuards`), parameter decorators for path parameters, headers and the body type, and an optional global-prefix call on a value created by a factory call (for example `AcmeServer.create(...)` followed by `app.setGlobalPrefix('v2')`). Permission decorators are recognised by name as for NestJS.
- **Import anchoring.** A decorator counts only when its local name is a named import (aliases included) or a namespace member of a specifier listed in `packages`, compared exactly. A file is examined only if it imports a family package or a subpath of it (`@acme/http/testing`, not `@acme/http-client`), but decorators imported from a subpath count only when that subpath is listed too. Decorators with the same names from another package, defined locally, re-exported through a barrel inside the repository, or not imported match nothing: there are no name-only matches. Relative specifiers in `packages` are matched literally.
- **Certainty.** As for NestJS: literal routes are `syntactic`, routes built from constants `resolved`, routes with dynamic segments `heuristic 0.40` (rule `declared-dynamic-route`). Endpoints carry `framework = <family name>`. A family's global prefix is its own entity, `other:http_family_prefix:<repo>:<family>:<prefix>`, and `atlas-link` composes it only onto that family's endpoints in the same repo (`declared-global-prefix`, `heuristic 0.85`, or `0.50` when several prefixes compete); NestJS endpoints only receive `http_global_prefix` prefixes, even when both use the same value.
- **Observability.** `catl status` and `atlas_status` print one line per enabled family with the controllers and routes it matched; a family that matched nothing, or one that is enabled but has no file, is printed as a warning, so a typo in a package or decorator name is visible.

Certainty highlights: literal routes and explicit table names are `syntactic`; computed routes, guard-to-scheme mapping, Prisma model calls (0.6), TypeORM default table names (0.6) and scheduler calls (0.7) are `heuristic`. Detector output is combined by the link pass into cross-repo facts (`calls_endpoint`, `supports_auth`, `uses_auth`, event producers and consumers), which are always `heuristic`.

## Experimental

Events, jobs and DB detectors tag every entity and edge they emit with `attrs.experimental = true`, and all their facts are heuristic. They assume one event bus and one logical database per project (events, queues and tables are project-scoped). Unmeasured: the quality evaluation checks the acme and globex event and `db_model` expectations (all found) but there is no precision measurement on real code. Treat them as leads.

Also experimental: LLM enrichment (inferred similarity verdicts) and rename lineage confidence calibration. See [trust and limitations](trust-and-limitations.md).

## Not supported

Other languages; GraphQL, gRPC, tRPC and RPC-style clients; HTTP clients other than those listed (`got`, `ky`, `superagent`, `ureq`, `hyper` clients); ORMs not listed (Drizzle, Diesel, SeaORM, Mongoose); message brokers beyond the bus-word heuristic; infrastructure files; environment value files.
